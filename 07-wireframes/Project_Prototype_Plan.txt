1. CHOSEN USER JOURNEY

Actor and goal (one sentence):
An authorised user (exact role to be confirmed, Q01) wants to view the student
support appointments scheduled for a particular date that they are permitted to see.

Why this journey:
- It is the most directly supported requirement in the catalogue (FR01).
- It already has a use case narrative (UC01), a use case diagram (UC-D01) and an
  activity diagram (AD01), so the prototype can be checked against those models.
- It raises the main unresolved issues: which roles may view appointments and what
  each can see (Q01, FR05, NFR02), and what personal information is necessary (Q03, NFR01).

3. OPEN QUESTIONS THAT AFFECT THE SCREENS

- Q01: Which roles may view appointment details, and what can each role see?
  (ask: support staff / service manager)

  (ask: support staff and the privacy contact)

  this to be confirmed.

- What is shown when a selected date has no appointments?


4. DRAFT WORDING FOR SECTION 4.1 OF THE PROJECT REPORT

4.1 Selected user journey

The prototype illustrates one user journey: an authorised user viewing the student
support appointments scheduled for a chosen date. The user opens the appointment
schedule, selects a date and, if the permission check allows it, sees the appointments
for that date. If permission is not granted, appointment details are not shown.

This journey was chosen because it is the most directly supported requirement in the
catalogue (FR01). It already has a use case narrative (UC01), a use case diagram
(UC-D01) and an activity diagram (AD01), so the screens can be checked against those
models. It also exposes the main unresolved issues: which roles may view appointments
and what each role may see (Q01, FR05, NFR02), and what personal information is
necessary (Q03, NFR01). A prototype can make those questions concrete for stakeholders.

No stakeholder has confirmed that this is the most important journey. Screens marked
as candidates (appointment details, access not permitted, no appointments) show
behaviour that is not yet specified and must be confirmed before it is treated as a
requirement.


5. RULES FOR THE PROTOTYPE

- Low-fidelity only: rectangles, labels and placeholders in diagrams.net. No working software.
- Dummy appointments and placeholder names only. Never use real student data.
- Describe any walkthrough honestly. A classmate or self-review is not a stakeholder.
- Mark screens that rely on unconfirmed behaviour as "candidate: needs confirmation".
