# Requirements Catalogue — Scenario B

**Status:** Version 0.3 (12 November 2026). Matches Section 2 of the project report. Requirements are candidate requirements based on Scenario B, the weekly labs, domain modelling (CD01) and prototyping. None have been confirmed by real stakeholders, and priorities are provisional.

| ID | Type | Requirement statement | Priority | Source | Rationale | Verification |
|---|---|---|---|---|---|---|
| FR01 | Functional | The system shall enable an authorised user to view scheduled student support appointments. | Must | Weeks 3–4 Labs. | Helps authorised users view scheduled appointments. | Check that an authorised user can view the agreed appointment information. |
| FR02 | Functional | The system shall display the student support services available through the college. | Must | Scenario B. | Helps students identify available services. | Check that the agreed service list is displayed. |
| FR03 | Functional | The system shall associate each appointment with the relevant support service. | Should | Scenario B; proposed detail. | Distinguishes appointments for different services. | Check that a test appointment is linked to the correct service. |
| FR04 | Functional | The system shall record the date and time of each appointment. | Must | Proposed appointment detail. | Identifies when appointments are scheduled. | Save a test appointment and check its date and time. |
| FR05 | Functional / access control | The system shall restrict appointment viewing to users with the required permission. | Must | Scenario B and Weeks 3–4 Labs. | Protects student appointment information. | Test access using accounts with different permissions. |
| FR06 | Functional | The system shall display the available appointment times for a selected support service. | Must | Scenario B; goal in Section 1.2; CD01 (AvailabilitySlot); prototype Screen 2. | Students currently cannot easily check availability without emailing or phoning. | Select a test service and check that only unbooked times for that service are shown. |
| FR07 | Functional | The system shall allow support staff to record the times they are available for appointments. | Should | CR03; CD01 (AvailabilitySlot). | Available times must come from staff, so students only see times staff can actually offer. Who manages availability is unconfirmed (Q02). | Record a test availability slot with a staff account and check it appears as an available time. |
| FR08 | Functional | The system shall allow a student to request an appointment for a selected support service and available time. | Must | CR02; Scenario B; prototype Screens 1–4. | Replaces the current process of arranging appointments by email or phone. Whether a request is booked instantly or needs staff approval is unconfirmed. | Request a test appointment and check it is recorded with the correct student, service, date and time. |
| FR09 | Functional | The system shall show the student a summary of the appointment details before the request is confirmed. | Should | Prototype Screen 4. | Lets the student check the service, date and time and correct mistakes before confirming. | Complete the booking steps and check the summary matches the selections made. |
| FR10 | Functional | The system shall allow a student to view their own upcoming and past appointments. | Should | Scenario B; Section 3.5 finding; prototype Screen 6. | Students need to check what they have booked. FR01 covers the staff view of the schedule. | Sign in as a test student and check that only that student's appointments are listed. |
| FR11 | Functional | The system shall record the status of each appointment. | Should | CD01 (Appointment.status); Q04. | Staff need to know whether an appointment is booked, cancelled or attended. The status values are unconfirmed (Q04). | Create a test appointment and check its status is recorded as booked. |
| FR12 | Functional | The system shall allow an appointment to be cancelled in line with the agreed cancellation policy. | Should | Scenario B; Section 1.2 goal; Q01; prototype Screen 6. | Changes and cancellations are currently difficult to manage. Who may cancel, and any cut-off time, is unconfirmed (Q01, Q02). | Cancel a test appointment under the agreed policy and check its status changes and the time becomes available again. |
| FR13 | Functional / business rule | The system shall prevent an availability slot from being booked by more than one student. | Must | CD01 (AvailabilitySlot 1 — 0..1 Appointment); A01. | Avoids double booking, which is a risk with the current informal calendars. | Attempt to book the same test slot with two student accounts and check the second request is refused. |
| FR14 | Functional | The system shall send a confirmation to the student's college email when an appointment is booked. | Could | CR01; prototype Screen 5. | Gives students a record of their booking. Whether students want confirmations or reminders is unconfirmed. | Book a test appointment and check a confirmation is received at the test college email address. |
| NFR01 | Non-functional (privacy) | The system shall collect only personal information needed for the agreed appointment process. | Must | Scenario B and Week 2 Lab. | Avoids unnecessary collection of student information. | Review collected fields against agreed requirements. |
| NFR02 | Non-functional (security) | The system shall enforce the agreed access permissions for appointment information. | Must | Weeks 3–4 Labs. | Ensures access matches user responsibilities. | Test permissions for each confirmed user role. |
| NFR03 | Non-functional (accessibility) | The prototype should be reviewed against applicable accessibility criteria. | Should | Scenario B and project guidance. | Helps identify barriers to using the proposed screens. | Review the prototype against applicable accessibility criteria. |
| NFR04 | Non-functional (accessibility) | The student booking screens shall meet the applicable WCAG 2.2 Level AA success criteria. | Should | Scenario B; Section 1.2 goal (accessibility and usability); project guidance. | Students with disabilities must be able to book support, and Learning Support users are likely to include them. | Review the screens against selected WCAG 2.2 AA criteria, for example Use of Color, Labels or Instructions and Target Size (Minimum). |
| NFR05 | Non-functional (usability) | A student shall be able to book an available appointment within 3 minutes without assistance. | Should | Section 1.2 goal (ease the process of booking); prototype walkthrough. | A slow or confusing process would discourage students from booking support. The 3-minute target is a proposed value to be confirmed. | Time test users completing the booking journey and check they finish within 3 minutes without help. |
| NFR06 | Non-functional (security) | The system shall require users to sign in with their college account before viewing or booking appointments. | Must | Scenario B privacy concern; A02; Weeks 3–4 Labs. | Identifies the user so the correct access permissions (NFR02) can be applied and student data is protected. | Attempt to open the appointment screens without signing in and check access is refused. |

## Summary

- 20 requirements: 14 functional (including one business rule, FR13) and 6 non-functional.
- FR06–FR14 and NFR04–NFR06 were added in v0.3 after domain modelling (CD01) and prototyping showed the first catalogue only covered staff viewing appointments.
- CR01, CR02 and CR03 from Section 1.5 are now recorded as FR14, FR08 and FR07.
- Requirements that depend on unconfirmed rules: FR08 (instant booking or staff approval), FR11 (status values, Q04), FR12 (cancellation policy, Q01), NFR05 (3-minute target is a proposed value).
